## Software System

### Name

**UN Agent — *Asesores en Salud***

### Logo

![image15](https://hackmd.io/_uploads/SJtS7cRyze.png)

### Description

UN Agent is a multi-tenant conversational AI platform that automates patient-facing
administrative workflows in healthcare. Its first vertical slice handles hospital
appointment scheduling: end-users interact with a Telegram bot to list doctors, query schedules, book appointments, and request cancellations. The agent runs a tool-calling loop (≤ 5 rounds) against a hospital scheduling API and streams natural-language replies token-by-token via Server-Sent
Events (SSE).

#### Architectural styles and patterns

| Pattern | Meaning | Implementation |
|---|---|---|
| **Microservices Architecture** | Decomposes the application into loosely coupled, independently deployable services organized around business capabilities. | The system is split into specialized, single-responsibility services (`chat-orch`, `agent-runtime`, `tenant`, etc.) written in diverse languages (Rust, Go, Python, TypeScript, Java). |
| **Backend-for-Frontend (BFF) / API Gateway** | Provides a single entry point for clients, aggregating responses and hiding the complexity of internal microservice communications. | `chat-orch` (Rust) acts as the central synchronous orchestrator, receiving HTTP requests from the frontend and distributing the workload downstream. |
| **Publish–Subscribe (Event-Driven)** | Enables asynchronous, non-blocking communication between services via message queues, ensuring the main application thread is not delayed by background tasks. | RabbitMQ is used to decouple non-critical paths — such as `compliance` audit logging and `email-send` dispatch — from the main user request/response cycle. |
| **Client–Server / Request-Response** | A standard synchronous communication model where a client requests resources from a centralized server, which processes and returns the result. | Handled via synchronous HTTP REST connections between the frontend, `chat-orch`, and downstream application components. |
| **Streaming (SSE)** | Enables unidirectional, real-time event streams from the server to the client over a single HTTP connection. | Utilized to deliver LLM agent replies token by token directly to the client interface, providing a highly responsive chat experience without polling. |
| **Secure Channel (Encrypted Communication)** | Ensures the confidentiality, integrity, and authentication of data in transit by encrypting the communication links between clients, gateways, and internal components. | Enforced by requiring HTTPS/TLS for all external REST and SSE traffic terminating at the Cloudflare edge/NGINX proxy, and utilizing encrypted data streams for internal synchronous communications between `chat-orch` and downstream microservices. |

#### Architectural elements and relations

The system is organized into five layers with a strict downward-dependency rule —
a layer may use only the layer directly below it.

| Layer | Responsibility | Elements |
| --- | --- | --- |
| Presentation | End user or tenant interaction | Web app (client + admin dashboards), Telegram client, NGINX |
| Connection | The single door in. Takes every request and points it at the right service | chat-orch |
| Logic | The logic that manages the  main functionalities: chat, auth, audit, emails, async messaging | agent-runtime, conversation-chat, tenant, user-auth, compliance, email-send, RabbitMQ |
| Data | System persistency  | PostgreSQL, MongoDB, Redis |


#### Architectural Patterns

| Pattern | Meaning | Implementation |
|---|---|---|
| **Layered architecture**  | *Meaning:* Organizes system components into horizontal, stacked tiers, effectively separating concerns like user interface, business rules, and data access.  | *Implementation:* The system is structurally divided into five distinct domains: Presentation, Gateway/BFF, Application/Domain, Integration, and Data.  |
| **Strict Layering** | Each layer can use only the layer immediately below — no skipping, no calls upward, no cycles. | Presentation calls only the Gateway; the Gateway calls only Application; Application reaches only Integration or Data. The use-graph has no cycles. |

## Quality Attributes


### Security

The system addresses four security scenarios, each met by one architectural
countermeasure. Each scenario is analysed through six components — Weakness, Threat,
Attack, Risk, Vulnerability, Countermeasure.


#### Scenario 1 — Inter-service confidentiality (Secure Channel).
![Canal seguro](https://hackmd.io/_uploads/SyqSQ8ZlGx.png)


##### Architectural Pattern
**Secure Channel** — application-layer AES-256-GCM encryption envelope (`seal` / `open`) on every backend-to-backend message; integrity guaranteed by the AEAD tag.

##### Architectural Tactics
| Goal category | Tactic | Application | Pattern |
| --- | --- | --- | --- |
| Resist attacks | Encrypt data | AES-256-GCM envelope on every internal HTTP/AMQP payload. | Secure channel |
| Resist attacks | Verify message integrity | AEAD (authenticated encryption with associated data) authentication tag rejects any tampered ciphertext. | Secure channel |

#### Scenario 2 — Direct backend access and information disclosure (Reverse Proxy).
![Proxy - Página 1](https://hackmd.io/_uploads/SkonpBbeze.png)


##### Architectural Pattern
**Reverse Proxy / API Gateway** — NGINX single origin (port 3000) routing by URI prefix to upstream services, terminating TLS and stripping `X-Powered-By` / `Server` headers.

##### Architectural Tactics
| Goal category | Tactic | Application | Pattern |
| --- | --- | --- | --- |
| Resist attacks | Limit exposure | Single public origin (NGINX) on port 3000; upstream services not directly addressable from the public network. | Reverse proxy |

#### Scenario 3 — Unrestricted lateral movement to databases (Network Segmentation).
![Network Segmentation - Canal Seguro](https://hackmd.io/_uploads/HJW9-8-xGe.png)


##### Architectural Pattern
**Network Segmentation** — three-zone segmentation plus micro-segmentation and exclusive ownership networks; isolation empirically verified with per-network connectivity probes (a *bad address* DNS failure proves the target is invisible, not merely blocked).

##### Architectural Tactics
| Goal category | Tactic | Application | Pattern |
| --- | --- | --- | --- |
| Resist attacks | Separate entities | Exclusive Docker network per service↔DB pair (`email-send` cannot resolve `tenant_db`). | Network segmentation |
| Resist attacks | Limit exposure | Databases have no exposure on public or orchestration networks. | Network segmentation |

#### Scenario 4 — Request flooding and brute-force abuse (Throttle Requests).
![Throttle - Página 1](https://hackmd.io/_uploads/HJW63BbxMg.png)

##### Architectural Pattern
**Rate Limiting / Throttling** — token-bucket limiters at two tiers: chat-orch (`tenant_chat` 20-req burst / 1 req·s⁻¹; `tenant_feedback` 10-req burst / 0.5 req·s⁻¹) and tenant (`/auth/login` 5-req burst / 1 req·30s⁻¹); all thresholds environment-configurable.

##### Architectural Tactics
| Goal category    | Tactic                   | Application                                                                    | Pattern    |
| ---------------- | ------------------------ | ------------------------------------------------------------------------------ | ---------- |
| Resist attacks   | Limit access             | Token-bucket limiter caps requests per tenant id / client IP.                  | Throttling |
| React to attacks | Inform actors            | HTTP 429 + `Retry-After`; frontend Axios interceptor renders a cooldown toast. | Throttling |
| Detect attacks   | Detect denial of service | Token-bucket exhaustion is the DoS detection signal.                           | Throttling |

#### Additional Tactics Applied
The following tactics are applied across the system but were not raised as their own scenarios above.

| Goal category | Tactic | Application | Pattern |
| --- | --- | --- | --- |
| Resist attacks | Authenticate actors | JWT (HS256) with `user_id`, `role`, `tenant_id` on administrative endpoints; `X-Internal-Key` for the orchestrator. | Valet key |
| Resist attacks | Authorize actors | RBAC across `app_admin`, `tenant_admin`, `tenant_operator`. | Valet key |
| Detect attacks | Detect intrusion | Structured JSON logs with `tenant_id`, `request_id`, `user_id` on every request. | Audit logging |
| Recover from attacks | Maintain audit trail | Every rejection / external call is persisted to MongoDB via compliance. | Audit logging |


### Performance and Scalability

The performance test follows the standard quality-attribute test format: scenario,
test scope, hardware allocation, infrastructure, load profile, results and analysis.

#### Performance Tactics Implemented

| Tactic | Description |
|---|---|
| **Manage Work Requests** | A token-bucket rate limiter in `chat-orch` (`rate_limit.rs`) caps chat requests at 1 req/s (burst 20) and feedback at 0.5 req/s (burst 10), preventing any single client from flooding the pipeline. |
| **Limit Event Response** | The same limiter returns `HTTP 429 + Retry-After`, and the frontend (`axios.ts:48-62`) reacts by throttling the UI automatically. |
| **Reduce Computational Overhead** | Redis caches hot session state in `conversation-chat` to avoid repeated MongoDB round-trips, and JWT verification is stateless (HS256), eliminating a DB hit on every authenticated request. |

#### Path of the tests

The test targets the end-to-end chat flow starting at the frontend NGINX reverse proxy
(`http://localhost:3000`), which routes `POST /v1/chat` exactly as a browser would.
The path under test:

```
k6 -> frontend nginx (:3000) -> chat-orch (:8000)
    -> agent-runtime (:3100)
        -> conversation-chat (:8082)
            -> Redis (session cache)
            -> MongoDB (session history)
            -> RabbitMQ (async queue)
    -> llm-mock (:9999)   <- replaces OpenRouter
```

**LLM isolation.** OpenRouter is replaced by a deterministic mock (`llm-mock`,
Node.js/Express) with a fixed 800 ms delay (`LLM_MOCK_DELAY_MS=800`). Any latency
beyond the 800 ms baseline is pure platform cost.

#### Hardware allocation

Load tests were executed on a dedicated single-node Kubernetes cluster
(24 vCPU / 27 GB RAM Linux machine), separate from the production GKE
deployment. Resource limits are enforced per pod via `resources.limits`.

#### Load profile

A staged ramp (`options.stages`): each level is a 1-minute ramp plus a 1-minute hold,
16 minutes total — 0→10, 10→50, 50→100, 100→200, 200→500, 500→750, 750→1 000,
1 000→2 000 VUs. Each VU sends a `POST /v1/chat` with a simulated medical-scheduling
message, then waits 0.5–2 s think time.

#### Results and analysis

![image14](https://hackmd.io/_uploads/BkMCXqCJzg.png)

From the load tests, we define the performance curve taking error requests as unresolved requests.

![curva_rendimiento_knee (1)](https://hackmd.io/_uploads/rkmdx7Zlfx.png)


*UN Agent performance curve, Batch 8, max 2 000 VUs — average response time and error rate.*

| Zone | Range (VUs) | Latency (ms) | Error Rate |
| --- | --- | --- | --- |
| Stable Zone | 10 – ~700 | ~800 (flat) | 0% |
| Knee Point | ~700 | ~1 100 (rising) | First error > 0% |
| Degradation Zone | 1 000 – 1 200 | 1 100 – 1 500 | < 5% |
| Saturation Zone | 1 200 – ~1 800 | 1 500 – 2 153 | 5 – 10% |
| Collapse | ~1 800 – 2 000 | ~1 700 (artifact) | > 85% |

- **Stable zone (10 – ~700 VUs).** Latency stays flat near 800 ms — dominated by the LLM-mock delay — at 0% errors. The system scales linearly; no resource is consistently saturated.
- **Knee point (~700 VUs).** The first non-zero error appears and latency starts rising (~900 ms): internal queues and connection pools begin to contend.
- **Degradation / saturation (1 000 – 1 200 VUs).** Latency climbs from ~1 100 ms to ~1 500 ms; error rate crosses 5%. The connection pools of conversation-chat and its stores (Redis/MongoDB) begin rejecting connections.
- **Collapse (~1 800 – 2 000 VUs).** Two failure modes: HTTP 502 Bad Gateway (code 1502, the majority — fast ~5 ms rejections from an exhausted upstream pool) and request timeouts (code 1050, the 15 s client timeout). Error rate jumps to ~85%.
- **Apparent latency drop at high VUs.** The curve declines after its 2 153 ms peak at 1 664 VUs. This is a statistical artifact: fast 502 errors pull the arithmetic mean down. The peak is the last stable point, not a recovery.
